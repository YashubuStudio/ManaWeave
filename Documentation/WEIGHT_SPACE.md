# Weight-Space Magic の実装

## 参照と採用範囲

ユーザー指定資料：Rikiya Takehiほか、**Sparks of Weight-Space Programming: LLMs can natively read & write neural network weights**、2026-11-02。

https://rikiyat.github.io/blog/weight-space-programming/

この記事の「仕様を理解し、ネットワークの重みへ直接書き込む」という考え方を、ゲーム内の有限な魔法命令に適用しました。記事の実験結果を本プロジェクトの性能実証として流用していません。記事のMinAtar・GoネットワークやQwenの重みを使用していません。

## 今回の直接構成

`LLM/weightspace/compile_weights.py` が、語彙埋め込みと3つのアフィン変換に対する数値を直接作成します。学習ループ、損失最小化、勾配、外部チェックポイントを使いません。

1. UnicodeをNFKC正規化し、決めた語彙で最長一致のトークン化をします。
2. 各語彙の埋め込みベクトルを読み込み、最大値プーリングで操作・大小・素材・拒否に関する特徴を集めます。
3. 第1層は既定値と競合条件を計算します。操作がない、複数ある、大きさが矛盾する、などの特徴を含みます。
4. 第2層のReLUゲートが、操作・大きさ・出力位置を組み合わせます。
5. 出力層が、操作、半径、出力、素材、終了のトークンを生成します。未知語や対応外条件は拒否側の出力を選びます。

二値特徴のANDは `ReLU(a+b+c-2)` として記述できます。これを各命令の条件に展開して、実数行列へ書き込んでいます。C#側はこの行列を読み、埋め込み・積和・ReLUを計算します。重み生成時のPythonをゲーム内で実行する構成ではありません。

**これは有限の仕様を数値ネットワークへ構成した条件付きトークン変換器です。Transformerではなく、任意の日本語を推論するLLMでもありません。** 別途同梱したRuneLMは、実際に学習した自己回帰Transformerです。この区別は実装とUIに保持しています。

## ファイル形式

`wsp_model.bytes` はリトルエンディアンです。

- 先頭4bytes：`MWSP`
- int32 × 7：形式バージョン、語彙数、特徴数、入力数、第1隠れ層幅、第2隠れ層幅、出力語彙数
- 入力語彙および出力語彙：UTF-8、int32のバイト長＋本文
- float32：埋め込み、W1、b1、W2、b2、W3、b3を行優先で格納

最終配布版は **6,140パラメータ、27,932bytes** です。データや命令を数値として詰め込むためだけに巨大化させた0.1Bモデルではありません。

生成は以下で再現できます。NumPyのみを使用します。

```bash
python LLM/weightspace/compile_weights.py
```

## 検証の意味

`evaluation.json` の1,168ケースは、作者が定義した語彙・文法に基づく組み合わせと拒否例です。直接構成したネットワークの仕様適合性のテストであり、未知の日本語に対する一般化精度ではありません。行列の値はこれらの出力誤差から学習していません。

`parity_fixture.json` はPython側のロジットと生成トークンを保存しています。C#側の `WeightSpaceMagic.PredictLogits` と比較し、実際に一致を確認します。

共通の入力検証はさらに保守的です。ネットワーク単体が出力できる表現でも、共通検証が拒否する場合があります。モデル単体の正答率と、ゲーム内で受理する割合を同一として報告しません。

## ゲームへの統合

`MagicParser` は専用DSLを先に確定的に処理し、通常の自然文では選択された解析方式を使います。既定は直接構成した重みです。ユーザーはワークベンチで学習型Transformerへ切り替えられます。

解析器はUnityのオブジェクトや世界状態を触りません。`MagicParseResult` の命令候補を返し、照準の位置と現在の資源状態は発動時に解決します。拒否された文を別モデルで黙って解釈し直して発動するフォールバックはありません。

数値、条件分岐、複数操作、対象フィルターのような自由度を広げる場合は、まず中間表現を拡張し、その正確な意味と検証器を決めます。その後に行列構成や学習データを拡張します。モデルが知らない効果を説明文だけで世界に追加することはできません。
